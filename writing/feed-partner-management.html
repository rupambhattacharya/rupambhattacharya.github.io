Automating Content Ingestion From 200+ Partners

April 2026 9 min read Architecture · Content Systems

Before this system existed, bringing in a new content partner — a wire service, a press agency, a niche publisher — meant a developer writing new integration code against a legacy Java application. That doesn't scale to 200+ partners across Germany, including major sources like Deutsche Welle, AFP, and Presse Portal, each with their own feed format and their own level of trust. I refactored that app into a config-driven Node.js/TypeScript service where onboarding a new partner is a document you create, not a deploy.

Two entities carry the whole system

EntityKey fields
PartnerContract terms, revenue share, a Salesforce-linked ID, and an isPartner flag that pre-filters who's even eligible for import
FeedSource URL, format (XML/JSON), a cron schedule, field-mapping rules, and the mode that decides what happens to whatever it imports

Partner records aren't hand-maintained either — a scheduled job syncs contract and billing data from Salesforce on its own cycle, so the CRM stays the source of truth for anything commercial, and engineering only owns the feed configuration layer on top of it.

Draft or auto-publish is a config value, not a code path

This is the decision that matters most: a new, unproven partner's feed is set to create content as drafts, so an editor reviews before anything goes live. A trusted, long-running wire service can be configured to publish straight through. Both are the same pipeline — the only difference is one field on the feed document.

same pipeline, one config field decides the outcome

A quality gate before anything reaches an editor

Parsing doesn't just extract fields — it validates them against publishing rules before content is saved at all, catching problems an editor shouldn't have to: 

if (teaserType === 'image' && mainImage) {
  if (!mainImage.caption) errors.push('Teaser image must have a caption');
  if (!mainImage.credits) errors.push('Teaser image must have credit');
  else if (mainImage.credits !== 'iStock') errors.push('Teaser image credit can only be iStock');
}
// inline images without credits are stripped, not just flagged
content = content.filter(p => p.type !== 'IMAGE' || !!p.credits);

Scheduling, cleanup, and knowing when a partner goes quiet

Scheduled jobWhat it does
Periodic content fetchPulls every feed due on its own cron, batches the import, and logs invalid feed IDs and failed imports by name
Content cleanupAuto-unpublishes content after a per-feed retention window, so nothing has to be manually expired
Partner syncPulls contract and billing data from Salesforce on a schedule, keeping partner records current without manual entry

Two email hooks close the loop operationally: one fires when a partner's feed goes quiet for days — often the first sign something broke upstream — and one fires when new content actually lands, so the team isn't watching a dashboard to know the pipeline is alive.

What the refactor actually bought

The old Java app's failure mode was that every new partner was a code change. The rewrite's whole point was to make that a config change instead — a new partner is a feed document with a mapping and a trust level, not a deploy. That's the same instinct behind every schema-driven system I've built: push variation into data the platform already knows how to read, instead of into code paths that have to be maintained by hand.

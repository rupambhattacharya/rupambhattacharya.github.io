Automating Content Ingestion From 200+ Partners

April 2026 10 min read System Design · Content Systems

This system has two jobs that are easy to conflate and expensive to conflate badly. The first is being a foundation: a generic, schema-driven content API every editor and every other content-touching workflow builds against, so nobody outside this system re-implements "what an article is" for their own purposes. The second is being an ingestion pipeline: automating the intake of XML and JSON feeds from 200+ German content partners — Deutsche Welle, AFP, Presse Portal among them — correctly capturing not just text but the images and video references bundled with it, and deciding per feed whether that content is trusted enough to publish itself. At full run rate that pipeline generates around 5,000 articles a day. The legacy Java application this replaced only really did the second job, and did it as one-off code per partner. Splitting the two cleanly is what let it scale to both.

Two jobs, one foundation

the pipeline is the biggest consumer of the foundation, not a separate system from it

Because ingestion is just another client of the same generic API — the same content, feed, and partner schemas, the same list/get/post/validate contract every other consumer gets — a partner-sourced article and an editor-written one are indistinguishable to anything downstream. That's deliberate: nothing downstream should need to know or care whether a given article arrived by RSS or by hand.

Getting content in correctly means more than parsing text

A feed parser that only extracts headline and body text is an incomplete parser — most partner feeds carry an image, sometimes a caption, sometimes credit information, spread across several possible tag conventions depending on the partner's RSS dialect. The parser has to check each in order before giving up:

What's neededWhere it's looked for, in order
Image sourcemedia:content URL → RSS <enclosure> → a bare <image> tag
Image creditmedia:credit inside the media block → a top-level media:credit → a partner-specific field_credit
Fallback imageIf none of the above resolve, the first image URL matched directly out of the raw content body

Each result becomes a structured image block in the canonical schema — not raw markup, a typed object with a source URL, credit, and caption. That's what makes the next step possible: this pipeline resolves references to media. It doesn't own image storage, and it shouldn't — a separate module in the platform's rendering side downloads from that source URL, stores the file once, and serves every transformation of it from the edge. Ingestion's job ends at "here is a well-formed reference to an image with the right credit attached," which is exactly the boundary a system design review should draw: don't make the ingestion pipeline responsible for a problem (image storage, resizing, CDN delivery) that belongs to a different part of the system.

Draft or auto-publish is a config value, not a code path

A new, unproven partner's feed is set to create drafts, so an editor reviews before anything goes live. A trusted, long-running wire service can be configured to publish straight through. Both run through the identical pipeline — the only difference is one field on the feed document.

same pipeline, one config field decides the outcome
if (teaserType === 'image' && mainImage) {
  if (!mainImage.caption) errors.push('Teaser image must have a caption');
  if (!mainImage.credits) errors.push('Teaser image must have credit');
  else if (mainImage.credits !== 'iStock') errors.push('Teaser image credit can only be iStock');
}
// inline images without credits are stripped, not just flagged
content = content.filter(p => p.type !== 'IMAGE' || !!p.credits);

Two entities carry the trust model

EntityKey fields
PartnerContract terms, revenue share, a Salesforce-linked ID, and an isPartner flag that pre-filters who's even eligible for import
FeedSource URL, format, a cron schedule, field-mapping rules, and the mode that decides draft vs. auto-publish

Partner records sync from Salesforce on their own schedule rather than being hand-maintained, so the CRM stays the system of record for anything commercial, and this system only owns the feed-configuration layer sitting on top of it.

Scheduling, cleanup, and knowing when a partner goes quiet

Scheduled jobWhat it does
Periodic content fetchPulls every feed due on its own cron, batches the import, logs invalid feed IDs and failed imports by name
Content cleanupAuto-unpublishes content after a per-feed retention window
Partner syncPulls contract and billing data from Salesforce on a schedule

Two email hooks close the loop: one fires when a partner's feed goes quiet for days, usually the first sign something broke upstream; one fires when new content lands, so nobody has to watch a dashboard to know the pipeline is alive.

The system-design takeaway: treat the ingestion pipeline as a client of the foundation, not a special case bolted onto it. Once a partner-sourced article and an editor-written one share one schema, one API contract, and one validation gate, nothing downstream ever has to know the difference — and "getting content in properly" stops meaning just text, because the schema already has a typed place for the image that came with it. At 5,000 articles a day from 200 publishers, that difference is the whole reliability story.

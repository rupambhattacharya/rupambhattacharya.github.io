One Schema, Three Brands: Designing a Common Content Model

April 2026 11 min read System Design · Platform Engineering

If you had to design a publishing platform from scratch for three brands — FOCUS Online, CHIP, Bunte — and the 20 engineering teams that ended up building on top of it, where would you actually start? Not with a database table. With the question every one of those teams and both of that content's audiences needs answered: an editor needs to write and preview an article; a reader needs it served fast, at the edge, with correctly sized images; and a team building a new content type needs to add one without waiting on a platform team. The system that answers all three ended up as five cooperating pieces, one schema running through all of them, and MongoDB Atlas as the only place any of them disagree about what's true.

The system, end to end

Strip away the code and this is the shape of it: an editor-facing CMS, a public renderer, a content API for everything else that needs to read or write, a scheduler for time-based state changes, and an edge layer that routes readers and handles image delivery — all reading and writing one shared MongoDB Atlas cluster, with a queue in between so legacy systems downstream hear about changes without being in the request path.

writes converge on Atlas; reads fan out through Akamai; changes leave through a queue, not a direct call

Every one of those five talks to MongoDB Atlas through the same generated client library, not five different data-access layers — which is the first place the schema pays for itself: one collection shape, one set of indexes, understood identically whether you're the CMS writing a draft or the scheduler flipping a state at midnight.

The schema underneath all five

The audit that made one schema possible was straightforward once done properly: title, lead text, lifecycle dates, and a state machine were identical across all three brands. Only which brand an entity belonged to needed to stay flexible — so brand became an enum value, not a schema fork, defined once in a shared primitives package every entity imports.

Shared primitiveWhy it's centralized
brand enumSo "brand" means the same thing to the CMS, the content API, the renderer, and the scheduler — not three subtly different things
state enumdraft / schedule / publish / unpublish, read identically by the scheduler cron and the renderer
Content block unionOne discriminated set of block types (text, image, gallery, quote, CTA…) instead of a body shape per brand
entityReferenceA custom schema keyword expressing relations MongoDB itself doesn't enforce

From there, the schema generates everything downstream — TypeScript types, MongoDB indexes, Swagger docs, and the runtime validation on every write — from one file, with a build step that refuses to let generated output and schema drift apart.

A widget is five packages, wired in automatically

Content itself follows the same instinct. A widget — gallery, quote block, partner module — is up to five packages: data-schema, rendering-page, editor-ui, and api. A CLI generator scaffolds all five from a template and wires each into the right application purely by naming convention, and rendering falls back to a shared core unless a brand explicitly overrides it:

every brand variant imports the same core logic; only layout differs

Frontend components: two different jobs, two different frameworks

The CMS and the renderer aren't the same kind of frontend, and the platform doesn't pretend they are. The CMS is a Vue application — forms, validation, drag-and-drop layout, the kind of stateful UI an editor tool needs. The renderer is built for pure read-side rendering speed, kept deliberately lighter. Both consume the exact same generated TypeScript types from the schema, so "what a gallery widget looks like" is never defined twice, even though the two apps that render it don't share a rendering framework.

Images: S3 as origin, Akamai as everything else

An uploaded image is downloaded once and stored in S3 — that's the only origin. Every actual transformation — resize, crop, region-of-interest around a focal point — happens at request time through Akamai's Image Manager, driven by query parameters generated per-image, per-placement: 

// Resize + focal-point-aware crop, generated on demand
im=RegionOfInterestCrop=(480,272),regionOfInterest=(3858,2860)

// URLs are hash-signed so Akamai only serves transforms this platform requested
hash = sha256(hashSecret + path + queryString)

That split matters architecturally: the platform never stores a pre-cropped variant for every brand and every placement. It stores one image and a focal point, and lets the edge compute whatever crop a given layout needs, on demand, cached at Akamai rather than recomputed per request.

Infrastructure: one ALB per service group, one monitoring module for all of them

The CMS, the content API, and the renderer each sit behind their own Application Load Balancer — separate blast radius, separate scaling — provisioned from the same Terraform module rather than three hand-written stacks. Monitoring follows the same pattern instead of three bespoke dashboards:

CMS ALB + logs ──┐ API ALB + logs ──┼──▶ shared monitoring module (per environment) Renderer ALB ──┘ │ ├──▶ CloudWatch dashboard (all three, one view) ├──▶ error-rate alarm (metric math: 5xx / total) └──▶ SNS ──▶ SQS ──▶ Lambda ──▶ Slack

A service group doesn't design its own alerting. It feeds an ALB and a log group into the module and gets a dashboard, a metric-math error alarm, and a Slack channel it didn't have to build.

The same instinct, five times over: one schema instead of three content models, one widget system instead of three ways to build a block, one ALB module instead of three load-balancer configs, one monitoring module instead of three dashboards, one image origin instead of per-brand pre-cropped variants. Nothing here required more discipline from any one team — it required the underlying thing to be declared once, so extending it could be self-service.

One Schema, Three Brands: Designing a Common Content Model

July 2026 12 min read Architecture · Content Systems · TypeScript

When I joined the team building the self-service publishing platform behind FOCUS Online, CHIP, and Bunte, each brand had grown its own way of modeling an article. Not wildly different — they were all "a headline, some paragraphs, an image, a state" — but different enough in the details that treating them as the same entity was a real question, not an assumption. Before I wrote a line of the new platform's data model, I spent time doing something less glamorous than architecture: reading through what each brand's content actually looked like in practice and writing down, field by field, what was shared and what wasn't. That audit is the part of this story I'd want another engineer to hear, because the schema design that came out of it is the reason a 200+ publisher, 3-brand platform runs on one API today instead of three.

Start with an audit, not a schema

The instinct when you're asked to unify three brands' content models is to start drawing boxes. I resisted that. The more useful first step was tabulating what fields each brand's content actually carried — title, lead text, SEO title, publish/unpublish dates, canonical URL, partner attribution — against which fields were brand-specific quirks that had accumulated over time rather than genuine differences in what an article is. Most of what looked like "brand-specific" turned out to be the same concept with a different name, or a field only one brand happened to be using because nobody had removed it. The genuine variation was much smaller than the apparent variation, and it mostly lived in one place: how the body of an article was structured.

What stayed common

Once the noise was filtered out, the shape that emerged was consistent across all three brands: an entity has a title, a lead text, an SEO title, a set of lifecycle dates (create, change, publish, unpublish), a state, and attribution back to a partner and a feed if it came from syndicated content. None of that needed to fork by brand. What did need to stay flexible was which brand a given piece of content, category, or feed belonged to — and that turned out to be a value, not a schema difference.

EntityCollectionBrand handling
ContentcontentsOne shared schema; brand resolved via feed → partner chain or set directly on the document
CategorycategoriesExplicit brand enum field: FOCUS Online, CHIP, Bunte
FeedfeedsBrand-agnostic; per-feed mapping config handles partner-specific quirks
PartnerpartnersShared across brands; a partner can syndicate to more than one

That single decision — brand is a field, not a fork — is what let three publishing pipelines become one. The alternative, which is what a rushed unification usually produces, is three parallel schemas with 90% overlapping fields and three parallel code paths to keep in sync forever. I'd rather spend the audit time up front than pay that tax on every future change.

What actually varied: the article body

The one place brands genuinely differed was in the kinds of content blocks an article could contain — quotes, embedded galleries, CTA buttons, partner-syndicated blocks, inline social embeds. Rather than pick a lowest common denominator (which would have broken brands that needed the richer blocks) or keep three separate body schemas (which would have broken the "one platform" goal), I modeled the body as a discriminated union: an array where every item is one of a fixed set of typed block schemas, disambiguated by a type field.

  • TEXT — plain paragraph content, with an optional highlight-block flag
  • IMAGE — with dimensions, focal point, credits, and its own lifecycle dates
  • GALLERY, ARTICLE — references to other entities by UUID
  • QUOTE, SOCIAL, SCRIPT, RAW — brand-specific embed and formatting needs
  • CTA — affiliate and call-to-action buttons, one of the more field-heavy block types
  • PARTNER — content attributed to and rendered on behalf of a syndication partner
export const ParagraphSubdocumentSchema: definitions.RelationalJSONSchema4 = {
  title: 'IParagraphSubdocument',
  type: 'object',
  oneOf: [
    TextParagraphSubdocumentSchema,
    ImageParagraphSubdocumentSchema,
    ScriptParagraphSubdocumentSchema,
    SocialParagraphSubdocumentSchema,
    ContentParagraphSubdocumentSchema,
    GalleryParagraphSubdocumentSchema,
    RawParagraphSubdocumentSchema,
    QuoteParagraphSubdocumentSchema,
    CTAParagraphSubdocumentSchema,
    PartnerParagraphSubdocumentSchema,
  ],
};

Every brand uses a subset of this union; none of them needed a block type outside it. That's the part I'd point to as the actual "common schema" work — not just merging the top-level article fields, which was mostly straightforward, but finding the finite set of content-block shapes that covered every brand's editorial needs without over-generalizing into a schema so loose it stopped catching mistakes.

Shared primitives, not copy-pasted definitions

Once the per-entity schemas were settled, a second-order problem showed up: the same concepts — a UUID, a date, the brand enum, the publishing state machine — were getting redefined slightly differently in each model file. That's the kind of drift that's invisible until a validation bug shows up in production because one schema's state enum quietly diverged from another's. The fix was a small shared package with the primitives defined exactly once: 

export const brand: JSONSchema4 = {
  enum: ['bunte', 'chip', 'focus'],
  description: 'Brand content',
};

export const state: JSONSchema4 = {
  enum: ['draft', 'schedule', 'publish', 'unpublish'],
  description: `State in which entity can be found itself:
  draft: Shown only in editor, not shown in OPM
  schedule: Will be shown at future date, not shown in OPM presently
  publish: Is visible in OPM
  unpublish: Entity is expired and no longer accessible in OPM`,
};

export const uuid: JSONSchema4 = { type: 'string', format: 'uuid' };
export const date: JSONSchema4 = { type: 'object', instanceof: 'Date', tsType: 'Date' };
The rule that made this stick: no entity schema is allowed to redefine what a date, a UUID, or a lifecycle state looks like. Every model imports these from one place. It's a small constraint, but it's the difference between "brand" meaning the same thing everywhere in the platform and "brand" meaning three subtly different things that happen to share a name.

Relations without a relational database

MongoDB doesn't give you foreign keys, but the platform's entities are genuinely relational — content references a feed, a feed references a partner, a paragraph block references an image or an article by UUID. Rather than lose that structure, the schema format itself was extended with two custom keywords: entityReference for a single relation to another entity, and entityMultiReference for a polymorphic relation resolved by a type discriminator — exactly the shape the paragraph union needed, since a GALLERY block and a CTA block relate to completely different target entities. 

export interface RelationalJSONSchema4 extends JSONSchema4 {
  entityReference?: {
    entityName: string;
    bindingProperty: string;
    entityPackageName: string;
  };
  entityMultiReference?: {
    bindingProperty: string;
    typeIdentifier: string;
  };
  properties?: { [k: string]: RelationalJSONSchema4 } | undefined;
}

This is metadata JSON Schema doesn't natively have an opinion about, so encoding it directly in the schema — rather than in a separate relations config that could fall out of sync — meant relation information traveled with the field it described. A build-time tool could walk the schema tree and know exactly which fields pointed where, without a human maintaining a second document that says the same thing.

One schema, four generated artifacts

The payoff for doing the modeling work carefully is that the JSON Schema stopped being documentation and became the only place these decisions were ever expressed. Everything downstream — the TypeScript types, the database layer, the API documentation, the runtime validation — is generated from it, not maintained alongside it.

content.model.schema.ts (JSON Schema — single source of truth) │ ├──▶ schema-to-interface-plugin ──▶ content.model.interface.ts │ (TypeScript interfaces, required-key types, generated at "rush build") │ ├──▶ manifest-extract-databases-plugin ──▶ MongoDB collection + indexes │ (collectionName, indexed fields, read from *.manifest.json) │ ├──▶ postman-collection-plugin ──▶ Postman collection │ (request/response shapes for API testing & docs) │ └──▶ ajv (runtime) ──▶ request/response validation (the exact same schema object validates incoming API payloads)

Every generated file carries the same header: DO NOT MODIFY THIS FILE BY HAND — modify the JSON Schema and run "rush build" to regenerate it. That convention is what makes the "single source of truth" claim actually true instead of aspirational — there's no second place for the type definition and the schema definition to quietly disagree, because one of them doesn't exist as hand-written code at all.

A generic API, not one per brand

The same discipline extends to the API layer. Instead of a controller per entity per brand, there's one generic controller factory — list, get, post, put, delete, search, validate — instantiated once per registered model: 

registry.forEach((module, name) => {
  router.get(`/${name}`, isApiKeyAuthorized('guest'),
    (req, res, next) => controller.listControllerFactory(module)(req, res, next));
  router.get(`/${name}/:id`, isApiKeyAuthorized('guest'), controller.getControllerFactory(module));
  router.post(`/${name}`, isApiKeyAuthorized('admin'), controller.postControllerFactory(module));
  router.put(`/${name}/:id`, isApiKeyAuthorized('admin'), controller.putControllerFactory(module));
  router.delete(`/${name}/:id`, isApiKeyAuthorized('admin'), controller.deleteControllerFactory(module));
  router.post(`/${name}/validate`, isApiKeyAuthorized('admin'), controller.validateControllerFactory(module));
});

The registry itself — which entity names map to which model packages — is generated too, extracted from package.json naming conventions rather than hand-maintained. Adding a new entity to the platform means adding a schema package; it doesn't mean writing a new controller, a new route file, or a new validation layer. That's the concrete mechanism behind "zero duplication of publishing logic": duplication isn't avoided by discipline alone, it's structurally impossible, because there's only one code path and it's parameterized by the schema.

Feeds don't get to see the canonical schema

One more seam mattered: 200+ partners send content as XML, RSS, or JSON, in whatever shape their own systems produce, and none of that is the canonical schema. The importer service normalizes each partner's feed into the common Content shape through a declarative per-feed mapping configuration — an XPath or JSON-path per target field, an optional fallback value, and a set of rules for where to insert derived content blocks. The partner's format is free to be whatever it is; the mapping configuration is the only thing that needs to change when a new partner with a slightly different feed shape onboards, not the schema, not the API, not the storage layer.

That decoupling is what let the platform scale to 200+ publishers without the canonical model absorbing 200 publishers' worth of special cases. The variation lives in configuration, one layer removed from the model everything else in the platform depends on.

What I'd do again

The lesson I keep coming back to from this project isn't really about JSON Schema specifically — it's that the audit is the design work. The three-brand unification succeeded because "brand" ended up being data (an enum value, a mapping config) rather than a code fork, and that only happened because the fields that were genuinely brand-specific got separated from the fields that just looked that way from years of divergent maintenance. Once that separation was right, treating the schema as the single generative source for types, storage, API, and validation was the easy part — and it's the part that keeps three brands and 200+ publishers from ever drifting back apart.

One Schema, Three Brands: Designing a Common Content Model

April 2026 10 min read Architecture · Platform Engineering

FOCUS Online, CHIP, and Bunte each modeled an article a little differently before this platform existed — same idea, different fields, different names for the same thing. Unifying them wasn't a redesign exercise. It was an audit: which fields were genuinely brand-specific, and which just looked that way after years of separate maintenance. The answer was almost entirely the latter. What came out of that audit — one schema, and a widget system built the same way — is what let six engineering teams extend a shared platform without a platform-team ticket for every change.

The audit: brand became a field, not a fork

Once the noise was filtered out, every brand's content shared the same shape: title, lead text, SEO title, lifecycle dates, a state machine, attribution back to a source. None of that needed to fork by brand — only which brand a piece of content belonged to needed to stay flexible, and that turned out to be a value, not a schema difference.

What variedHow it's handled
Which brand owns an entityA shared brand enum (bunte / chip / focus), defined once and imported everywhere
Publishing lifecycleOne shared state enum: draft, schedule, publish, unpublish — same meaning for every entity
Rich content blocksA discriminated union of block types (text, image, gallery, quote, CTA…), not a body schema per brand
Relations between entitiesA custom entityReference / entityMultiReference keyword, since MongoDB has no foreign keys of its own

Every one of those primitives lives in a single shared package. No entity schema is allowed to redefine what a date, a brand, or a lifecycle state means — which is the difference between "brand" meaning the same thing everywhere in the platform, and meaning three subtly different things that happen to share a name.

The schema generates everything downstream

Once that shape was right, the schema stopped being documentation. It became the only place these decisions get made — everything else is generated from it at build time, with a hard rule enforced by a comment at the top of every output file: modify the schema, not the generated code.

entity.schema.ts (JSON Schema — single source of truth) ├──▶ TypeScript interfaces (schema-to-interface plugin) ├──▶ MongoDB collection + indexes (manifest-extract plugin) ├──▶ Swagger / API docs (swagger-generator plugin) └──▶ Runtime request validation (same schema object, via ajv)

The API layer follows the same instinct: one generic controller — list, get, post, put, delete, search, validate — instantiated once per registered entity, instead of a hand-written controller per entity per brand. Adding an entity means adding a schema package, not a route file.

A widget is five packages, wired in automatically

The same discipline extends to content itself. A "widget" — a gallery, a quote block, a partner module — is up to five packages: data-schema, rendering-page, editor-ui, and api. A CLI command scaffolds all five from a template and registers each one exactly where it belongs, purely by naming convention:

PackageAuto-wired into
data-schemaStorage API, and the Renderer app too if the module has a page
rendering-pageRenderer app
editor-uiEditor UI app
apiEditor API app

A team's first commit on a new widget is already integrated into all four applications — no platform-team review step, because the naming convention and the schema contract are the review.

One widget, three brands, one fallback

Brands don't get their own copy of a widget either. Rendering code has a shared/ folder holding the real logic, and per-brand folders that override layout only where a brand actually needs to — falling back to a default/ variant otherwise.

every brand variant imports the same core logic; only layout differs

Monitoring three service groups without three dashboards

The platform isn't one service — it's several service groups, each with its own load balancer and log group. Rather than each building its own CloudWatch setup, there's one reusable monitoring module any service group plugs into, instantiated once per environment:

Service group A (ALB + logs) ──┐ Service group B (ALB + logs) ──┼──▶ shared monitoring module Service group C (ALB + logs) ──┘ │ ├──▶ CloudWatch dashboard (per group, one view) ├──▶ error-rate alarm (metric math: 5xx / total) └──▶ SNS ──▶ SQS ──▶ Lambda ──▶ Slack

The alarm is a metric-math query — 5xx count divided by request count — so it stays meaningful whether a service handles ten requests a minute or ten thousand. A service group doesn't design its own alerting; it feeds in an ALB and a log group, and gets a dashboard, an alarm, and a Slack channel it didn't have to build.

The same instinct, three times over: a shared schema instead of three content models, a shared widget system instead of three ways to build a content block, a shared monitoring module instead of three dashboards. None of it required more discipline from any one team — it required the underlying thing to be declared once, correctly, so extending it could be self-service.

Multi-LLM Evaluation Pipelines: Treating Prompts as Deployable Artefacts

July 2026 11 min read AI · LLMOps · Evaluation

Most teams that build with LLMs treat prompts as an implementation detail — a string interpolated into an API call, tweaked in place, redeployed with the rest of the code. That works until you have more than one prompt, more than one model provider, and more than one person editing them. At that point a prompt is no longer a string. It's an artefact with a version, a behavioural contract, and a blast radius if it regresses. It deserves the same discipline as any other deployable: review, versioning, and a test suite that runs before it ships.

This is the problem I've been chipping away at in llm-collab, an open-source CLI I built for orchestrating coding agents across providers. It started as "a tool to launch Claude Code with the right MCP servers attached" and turned into something closer to an LLMOps platform in miniature: config-driven model selection, cost and audit instrumentation on every inference, and — the part this post is about — prompts (I call them skills) shipped as versioned files with an evaluation gate in front of promotion, not behind it.

The core problem

A prompt is not portable by default

The moment you support more than one model provider — llm-collab talks to Anthropic, OpenAI, Ollama, and OpenRouter through the Vercel AI SDK — a prompt that was tuned against one model's instruction-following quietly degrades against another. Claude and GPT-family models don't weight system-prompt structure, tool-use hints, or formatting instructions identically. A prompt that reliably produces a clean JSON tool call on one model might wrap it in prose on another. You don't find this out by reading the prompt. You find it by running it.

The second complication is cost. If a prompt works equally well on a $0.80/M-token model and a $15/M-token model, shipping it against the expensive one by default is a standing tax with no upside. Evaluation has to report quality and cost and latency together, per candidate model, or "which model should this prompt run on" turns into a guess.

Skills as deployable artefacts

Markdown files, not string literals

The first design decision was to stop embedding prompts inside command handlers. Every prompt in llm-collab — what I call a skill — is a standalone Markdown file with YAML frontmatter declaring its dependencies explicitly: which model it targets, which tools it's allowed to call, and what has to be true in the environment before it can run. 

---
userInvocable: true
allowedTools:
  - github_get_pr
  - github_list_prs
  - github_add_comment
  - file_read
  - file_list
  - file_search
  - shell_execute
model: claude-sonnet-5
readinessCheck: "gh auth status"
requiredEnvVars:
  - name: GITHUB_TOKEN
    description: GitHub personal access token
    required: true
---

# Code Review

Review code changes for quality, correctness, and best practices.
...

Treating a skill as a file rather than a string buys three things immediately. It's diffable — a prompt change shows up in git diff like any other change and goes through the same PR review. It's installable and idempotent — llm-collab skills install writes it to ~/.claude/skills/ without clobbering a user's local edits, the same install/upgrade discipline you'd expect from a package manager. And it's rollbackable for free: reverting a bad prompt is git revert, not a hotfix to application code.

The reframe that matters: once a prompt is a file with a declared model and declared tool surface, "does this prompt still work" becomes a question you can automate an answer to — the same way "does this function still work" became automatable once you had a test file next to the source file.

Model selection is config, not code

The second piece is that llm-collab never hardcodes which model handles a task. Model choice is resolved through the same precedence chain as everything else in the CLI — CLI flag > environment variable > config file > default — and tasks are routed by declared complexity rather than a single fixed model: 

{
  "ai": {
    "default_provider": "anthropic",
    "default_model": "claude-sonnet-5",
    "complexity_routing": {
      "low": "claude-haiku-4-5",
      "medium": "claude-sonnet-5",
      "high": "claude-opus-4-8"
    }
  }
}

This matters for evaluation because it turns "which model should run this prompt" from a hardcoded assumption into a variable you can sweep. The evaluation harness doesn't test one prompt against one model — it tests a prompt against every model in the routing table it's eligible for, and the routing thresholds themselves get set from what the results show, not from intuition.

Instrumenting every inference

Cost and audit as evaluation signal

Every model call in llm-collab goes through a cost tracker and an audit logger, independent of whether you're in an interactive session or a scripted evaluation run. The cost tracker records input/output tokens against a static pricing table and writes a JSONL record per call: 

record(model: string, provider: string, inputTokens: number, outputTokens: number, command?: string): UsageRecord {
  const costUsd = getModelCost(model, inputTokens, outputTokens);
  const record: UsageRecord = {
    timestamp: new Date().toISOString(),
    sessionId: this.sessionId,
    model,
    provider,
    inputTokens,
    outputTokens,
    costUsd,
    command,
  };
  // append to ~/.llm-collab/costs/sessions.jsonl
  ...
}

The audit logger records the shape of the interaction — every tool_call, every decision, every error — as a typed, timestamped JSONL event, with an explicit event taxonomy rather than free-text logs:

EventFires on
command_start / command_endEvery CLI invocation
tool_callAny MCP tool execution, success or failure
decisionPoints where the agent chose between options
config_change / config_readConfiguration mutation or access
errorAny caught failure, with a redacted detail string

Neither of these was built for evaluation originally — they exist so a user can answer "what did this session cost me" and "what did the agent actually do." But once every inference already carries model, tokens, cost, and outcome, that log is the raw material an evaluation pipeline needs. I didn't have to add instrumentation to get evaluation data; I had to stop throwing away instrumentation I already had.

The evaluation gate

What "passing" needs to mean

The piece I'm building now — the honest "not finished yet" part of this post — is the harness that turns that raw instrumentation into a promote/reject decision, which I'm calling the arena: a benchmarking run that scores a candidate skill across every model it's routed to before it's allowed to replace the version currently installed. Two evaluation modes, because "good prompt" means something different depending on what the skill produces:

1

Skills arena — LLM-as-judge. For skills that produce open-ended output (a code review, a knowledge-capture summary), a fixed judge model scores candidate output against a rubric, blind to which model or prompt version produced it. This is the same pattern as the chronicle ask RAG path already in the CLI — semantic retrieval feeding a scored, cited answer — repurposed as a scoring function instead of a user-facing answer.

2

Agents arena — scenario-based. For skills that call tools (the github-expert and linear-expert domain agents, for instance), correctness isn't a judge's opinion — it's whether the right tool got called with the right arguments and the task actually completed. These run against fixed, replayable scenarios with assertions on the resulting tool-call trace, not the prose.

3

Cost and latency ride along. Every arena run reuses the existing cost tracker, so a scorecard isn't just "pass/fail" — it's quality delta against the current version, per model, with cost and p95 latency attached. A prompt that scores marginally higher but doubles cost on every eligible model is a decision, not an auto-promote.

Release and rollback, for free

Because skills are files under version control rather than state baked into a binary, "release" is a merged PR and "rollback" is a revert — the arena's job is only to gate what gets merged, not to manage a separate deployment artefact. That's the part of "deployable artefact" I care about most: I don't want a bespoke release process for prompts that doesn't already exist for code. I want prompts inside the one that does.

What I've learned so far

Portability is the wrong first question

I originally set out to write "provider-agnostic" prompts — phrasing that would work identically everywhere. That's the wrong target. Some prompts are worth specializing per provider if the eval data says so; the goal isn't one prompt that's mediocre everywhere, it's a routing table that sends each task to the model/prompt pairing that actually won the comparison.

Instrumentation you build for one reason pays for another

The cost tracker and audit logger were built so users could answer "what did this cost me" — a pure observability feature. They turned out to be exactly the data model an evaluation pipeline needs, with zero extra instrumentation. If you're building any kind of agent tooling, log inference input/output token counts and outcomes from day one, even before you know you'll need an eval harness. You will.

The judge needs its own eval

The failure mode I'm most wary of with the skills arena is a judge model that's inconsistent between runs. Before I trust it as a merge gate, the judge itself needs a small labeled set — cases where I already know the right answer — that it has to score consistently before its verdict on anything else counts.

What's next

  • Wire the arena into CI. A skill change opens a PR; the arena runs automatically against every model in that skill's routing table and posts a scorecard as a comment, the same shape as a test-coverage bot.
  • Judge calibration set. A small, versioned set of graded examples the judge model has to reproduce before its scores on new candidates are trusted.
  • Cost-aware routing suggestions. Once enough arena runs accumulate, have the CLI suggest routing-table changes — "this task tier is overpaying for quality it isn't using" — instead of leaving that judgment entirely manual.

None of this is exotic. It's the same discipline software engineering already applies to code — version control, review, a test suite that has to pass before merge — pointed at an artefact type we've been treating as disposable. The interesting part isn't the individual pieces; it's that once a prompt is a file with a declared model and a declared tool surface, all of those practices just apply, without inventing new tooling for them.

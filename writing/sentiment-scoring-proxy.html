A Sentiment-Scoring Proxy at 25M Requests

May 2026 7 min read AdTech · AWS · Caching

Every page view across FOCUS Online, CHIP, and Bunte needed a brand-safety sentiment score before ads could load against it — a signal our advertising team used to decide what could run next to what. That's a real-time constraint layered on top of a third-party dependency: a request volume in the tens of millions has to wait on someone else's API, or it can't. I built the proxy that made that trade-off manageable: cache-first, with a scheduled process keeping every cached score honest.

Cache first, third party last

For every URL, the proxy needed a sentiment score from Hyscore, a third-party scoring service. Calling it on every page view wasn't viable at this volume, so Redis sat in front of everything — serving up to 25 million requests directly. A miss fell back to the content platform's DynamoDB for the page's own data, then called Hyscore, then wrote the result back into Redis before returning it.

Redis in front of everything; Hyscore is a last resort, not a hot path

Why a TTL wasn't enough

Hyscore's sentiment scores aren't static — a page's score can shift as the story around it develops, and Hyscore refreshes on its own roughly 12-hour cycle. A simple cache TTL would mean the first request after expiry pays the full DynamoDB-plus-Hyscore round trip while ads wait. Instead, an AWS Step Functions state machine runs on that same 12-hour cycle and proactively refreshes cached scores ahead of expiry — so the common case at request time is still a Redis hit, even for content whose score just changed.

The design principle: keep the third-party dependency out of the request path entirely whenever possible. A state machine paying the Hyscore cost on a schedule is a very different reliability story than every ad request being one third-party outage away from failing.

What ownership end-to-end meant in practice

  • Reliability: Redis absorbing the vast majority of the 25M+ request volume meant a Hyscore slowdown degraded freshness, not availability.
  • Observability: cache hit rate, DynamoDB fallback rate, and Hyscore latency were each tracked separately — a healthy hit rate with rising Hyscore latency is a very different signal from a falling hit rate, and they needed different responses.
  • Cost: every avoided Hyscore call is a request that didn't hit a metered third-party API, which made cache hit rate a cost metric as much as a latency one.

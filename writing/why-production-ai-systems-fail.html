Building Production AI Systems That Actually Work

July 2026 13 min read AI · LLMOps · Production Engineering

Every AI feature I've watched hold up under real production load — and a few I've watched buckle — taught me the same lesson: the gap between a demo and a system you can trust in production is almost never about the model. It's about whether someone designed for eight specific, well-understood patterns before the first real user hit the system. None of these patterns are exotic, and none of them require a research breakthrough to fix. They're the same operational failure modes distributed systems have always had, showing up in a slightly new place, with a probabilistic component bolted on. The fix for each one is boring, well-documented engineering discipline — which is exactly what you want a reliability strategy to be.

This is the field guide I wish I'd had the first time I put an LLM-backed feature in front of real users: eight recurring patterns, and the concrete, current practice that addresses each one.

The eight patterns — and how to engineer around each one

1. Prompt/instruction fragility

A prompt that works reliably in testing shifts behavior on a phrasing change nobody flagged as significant, or drifts silently across a dozen small edits during iterative development. The fix starts with treating prompts as files under version control, not strings interpolated into a handler — reviewed in PRs, diffed like code, rolled back like code. The harder half of the fix is choosing what to test. Hamel Husain's guidance, developed with Shreya Shankar across dozens of production AI teams, is to resist writing evaluators for failures you imagine and instead do error analysis first: read actual production traces, categorize what's actually going wrong, count it, and only then build evals around the failure modes you've confirmed exist. Eval-driven development up front, before you have real traces to learn from, tends to produce evals nobody's failure distribution matches.

2. Retrieval/context failure (RAG)

Semantic mismatch between how users phrase questions and how your documents are written, context windows stuffed with irrelevant chunks, chunks that split a fact across a boundary — these are still the most common reason a RAG answer is wrong even though the model itself reasoned correctly over what it was given. The production-grade fix as of 2026 is hierarchical or sentence-window chunking — small chunks for precise matching, larger parent context for the model to reason over — combined with hybrid retrieval (vector plus keyword/BM25) and a cross-encoder reranking pass before anything reaches the context window. Reranking specifically is where a lot of RAG systems cross the line from prototype to production-grade: retrieval gets you a candidate set, reranking decides which of those candidates actually deserve to be there.

3. Hallucination/grounding failure

A model will answer confidently even when retrieval returned weak or irrelevant context, because the prompt structure implies an answer is expected. The mitigation is to make "insufficient information" a first-class, explicitly allowed output — not an edge case the model has to infer it's allowed to produce — and to enforce a grounding check between the generated answer and the retrieved passages before the answer ships, rejecting or flagging responses that assert claims the retrieved context doesn't support. Citation requirements do double duty here: forcing the model to attribute claims to specific passages makes ungrounded claims visibly absent a source, which is a far easier thing to catch automatically than judging factuality from the prose alone.

4. Latency & cost

Sequential pipeline stages compound into tail latency nobody budgeted for, and per-query cost multiplied by daily active users turns into a bill that ambushes finance before it ambushes engineering. Both get solved by the same two levers. Model routing — sending simple queries to a small, cheap model and reserving your most expensive model for genuinely complex reasoning — is reported to cut bills 40–85% with no visible quality drop, and the gap between the cheapest usable model and the most capable one on the market now runs to roughly 100x on a per-token basis — leaving a lot of the bill unearned if every query defaults to the expensive model. Semantic caching — matching incoming requests against cached responses by vector similarity rather than exact string match — removes duplicate inference calls entirely on workloads with real query overlap: FAQ systems, internal knowledge bases, support assistants. Combined, routing and caching are the difference between "AI feature" and "AI feature the CFO doesn't ask about."

5. Tool/agent orchestration failure

Multi-step agent systems fail in specific, well-catalogued ways: infinite handoff loops where agent A defers to B, B defers to C, and C defers back to A; tool-call timeouts cascading because nothing had a circuit breaker; context windows blown past their limit once you're coordinating four or more workers. The discipline that holds up in production treats tool failure as the common case, not the edge case — design the orchestration state machine assuming tools will fail, models will emit invalid arguments, and external APIs will time out, because in practice they will. Concretely: a durable request queue with backpressure, circuit breakers on every external dependency, bounded iteration counts so a loop can't run away, and rate limiting on the LLM calls themselves so one runaway agent doesn't starve every other request in flight.

6. Safety/guardrail gaps

Prompt injection remains, per OWASP's Top 10 for LLM Applications, the most persistent and hardest-to-fully-close attack class against anything that lets a model act on untrusted input. The practice that's converged on in production is defense-in-depth across layered rails rather than a single filter: input rails that classify and reject injection attempts before they reach the model, dialog rails that track multi-turn manipulation a single-turn classifier would miss, and output rails that catch it if an injection still got through. NeMo Guardrails and Guardrails AI are the two frameworks most teams reach for — NeMo for dialog and agentic flow control, Guardrails AI for composable output validation — and the two are commonly run together rather than as alternatives.

7. Observability blind spots

A team with no eval framework and no monitoring baseline finds out about a regression from a user complaint, not a dashboard — and by the time a user complains, the regression has usually been live for a while. The standard that's converged on for closing this gap is OpenTelemetry's GenAI semantic conventions: every LLM call, every tool invocation, every retrieval step becomes a child span with standardized attributes — model name, token counts, latency, finish reason — producing a full trace of the reasoning chain rather than a log line. It's now adopted across Google Cloud, AWS, Azure, and Datadog, which means instrumenting to this standard once buys you compatibility with whichever observability backend you or a future team picks.

8. Data/embedding drift

The failure mode with no error to catch: a RAG system that audits perfectly clean at launch quietly loses retrieval quality over months, because the corpus it indexes has drifted away from the distribution the embedding model or the chunking strategy was tuned against — or because a provider silently updated the embedding model and old and new vectors are no longer comparable in the same index. The concrete defenses are to pin embedding pipeline versions, never mix embedding generations in the same index, and track the rolling mean and variance of cosine similarity between queries and their top-k retrieved documents — a sustained drop of more than roughly two standard deviations is your early warning that retrieval is silently degrading, well before a user notices the answers got worse.

The thread running through all eight: every one of them is invisible on a standard uptime dashboard. Dashboards stay green, error rates look nominal, SLAs are met — and answer quality quietly decays underneath all of it, because the metrics you're watching were never built to measure the thing that actually degraded. That's why patterns 7 and 8 — observability and drift — are the two that make the other six catchable at all.

Frameworks that make this repeatable, not heroic

None of the above needs to be invented from scratch inside your org. The governance and operational scaffolding already exists, mostly ported over from a decade of MLOps discipline:

  • Google's Practitioners Guide to MLOps — defines CI/CD/CT (continuous integration, delivery, training), maturity levels 0–2, feature stores, and model/data validation. Google's own framing captures the whole point: "the real challenge isn't building an ML model... it's building an integrated ML system and continuously operating it in production."
  • Google's Secure AI Framework (SAIF) — organizes security controls across four areas: Data, Infrastructure, Model, and Application, addressing model theft, training-data poisoning, prompt injection, and confidential-data extraction.
  • NIST's AI Risk Management Framework — the closest thing to a regulator-neutral checklist for AI governance, useful as a shared vocabulary across legal, security, and engineering.
  • Eval-driven development, per Husain and Shankar — error analysis, then categorizing and counting failure modes, then building code-based and LLM-as-judge evals, then gating merges on those evals in CI/CD, then closing the loop with production telemetry. Custom, product-specific evals consistently outperform generic benchmarks, because a generic benchmark rarely resembles your actual failure distribution.

Treat production readiness as Phase 0, not a launch checklist

If I had to compress everything above into one instruction for a team about to ship their first production AI feature, it's this: define what "production-ready" means before the proof of concept, not after it demos well. In practice that looks like a short, concrete sequence:

1

Define evals and success metrics in week one. Not after the POC works — before it. If you can't state what "good" looks like, you can't tell when you've silently drifted away from it.

2

Instrument tracing from the first call. OpenTelemetry-based tracing as the foundational observability layer, not a retrofit after the first incident.

3

Set latency and cost budgets per pipeline stage. A single end-to-end SLA hides which stage is actually the problem when it's blown.

4

Add guardrails and grounding/citation checks before launch, not as a patch after the first bad output goes viral internally or externally.

5

Build the telemetry → triage → fix loop. Thumbs-down capture, root-cause categorization, and a path back into the eval set — this is the retention-and-adaptation loop most AI systems never build, and it's the difference between a system that stays good and one that quietly stops being good.

And know in advance which signals should override a launch decision. If P95 latency exceeds roughly two seconds, users churn regardless of answer quality — prioritize routing and caching over further accuracy gains. If per-query cost multiplied by daily active users threatens unit economics, add intent-based routing so simple queries hit a cheap model and only complex ones hit an expensive one. And if your offline eval pass rate is high but production thumbs-down is climbing, you don't have a prompt problem — you have drift, and the fix is monitoring, not more prompt tuning.

What actually separates the systems that hold up

None of the eight patterns above are exotic, and none of the fixes require a research breakthrough — chunking strategy, reranking, circuit breakers, layered guardrails, standardized tracing, drift monitoring. It's the same discipline that took web services from "it works on my machine" to five-nines availability, pointed at a new artifact type with a probabilistic component. The teams whose AI features hold up in production aren't the ones with the best model. They're the ones who treated these eight patterns as Phase 0 work — designed for before the first user hit the system — instead of a post-launch cleanup task discovered one incident at a time.
